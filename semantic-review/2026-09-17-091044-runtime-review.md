# Runtime crash & break risks in the cloud-sync-removal / startup-rewiring change

## Resolution status (updated)

**FIXED:**
- **#1 AppLockGate re-prompt on config change / process death** — unlock state is now held in `rememberSaveable`, so rotation, dark-mode toggle, font-scale change, and process death no longer force re-authentication mid-session.
- **#2 school-report gate always "premium required"** — the exam-detail `ReportViewModel` now receives the app-scoped `SubscriptionManager`, so school-level report tier-gating resolves correctly for Premium users.
- **#3 per-app locale silently not applied on API 26–32** — `MainActivity` is now an `AppCompatActivity` with `Theme.AppCompat.DayNight.NoActionBar`, so `AppCompatDelegate.setApplicationLocales` applies to the UI; this also averted a startup crash from the previously non-AppCompat theme.
- **#4 double app bar in the Analytics tab** — `ItemAnalysisPanel` is now hosted with `embedded = true`, dropping its own `Scaffold`/`TopAppBar` when rendered inside the tab region.
- **#7 dead `SmartDashboardMVP` fallback** — the unreachable fallback branch was removed and replaced with a graceful placeholder.

**DEFERRED (by product decision — do not touch billing/login yet):**
- **#5 billing not-ready / no on-demand reconnect** — currently fails gracefully (errors surface as toast/state, no crash); on-demand reconnect intentionally not added yet.
- **#6 `context as? Activity` null path in the subscription upgrade** — null-guarded so it no longer crashes; the deeper reconnect/flow rework is deferred.

**Note:** Separately, an out-of-review finding was fixed: bubble grading was mocked (random answers); the real detection pipeline is now wired via `BubbleGridMapper` + `BubbleSheetProcessor.processImage`. Scanning limitations (no perspective/deskew, app-printed single-page sheets only, on-device verification pending) are tracked in design.md §12.

This change removes the cloud-sync subsystem, moves DI/startup wiring into `ExamScannerApplication`
(lazy Billing client, per-app locale, WorkManager scheduling, `SubscriptionManager.initialize()`),
switches `MainActivity` to a `FragmentActivity` fronted by a biometric `AppLockGate`, and reshapes
`ExamDetailScreen` into Results/Analytics/Reports tabs that host the previously full-screen
`ItemAnalysisPanel`/`SmartDashboardMVP` inline. The code compiles and unit tests pass; the risks below
are the runtime behaviors the compiler cannot see.

Watch for: (1) the biometric `AppLockGate` re-authenticates on **every configuration change / rotation**
and after process death because unlock state is held in `remember`, not `rememberSaveable` — confirmed;
(2) school-level report generation is wired with a **null `SubscriptionManager`**, so it always shows
"premium required" even for premium users — confirmed; (3) `AppCompatDelegate.setApplicationLocales`
is applied against a plain `FragmentActivity` (not `AppCompatActivity`), so on API 26–32 the saved
locale silently does not apply to the UI — likely; (4) the nested `Scaffold`/`TopAppBar` from
`ItemAnalysisPanel` renders inside the tab region, producing a double app bar and duplicated insets —
confirmed cosmetic, not a crash.

**Verdict**: NEEDS_CHANGES

## High-level view

The `AppLockGate` lifecycle logic is guarded well enough against the biometric-dialog re-lock loop
(the `unlocked`/`prompting` flags short-circuit the ON_START that fires when the credential UI returns),
but the unlock flag lives in `remember`, so rotation, dark-mode toggle, font-scale change, or process
death drops the unlock and forces the teacher to re-authenticate mid-session. That is the single most
likely "why does it keep asking me" complaint.

The billing wiring is thread-correct (`launchBillingFlow` ends up on the main dispatcher) and tolerant
of an unconnected client (errors surface as toast/state, not crashes). The functional gap is elsewhere:
the exam-detail `ReportViewModel` is built with no `SubscriptionManager`, so the school-report gate
resolves to "upgrade required" unconditionally — a paid feature that can never fire.

The analytics tab hosts `ItemAnalysisPanel`, which still carries its own `Scaffold` + `TopAppBar` +
`fillMaxSize` `LazyColumn`. Inside the tab it renders under a bounded height, so there is no
infinite-constraint measurement crash, but the user sees two stacked app bars and the panel's own
"back" arrow that does nothing. `SmartDashboardMVP` (the fallback branch) is effectively dead code
because `analyticsViewModel` is always non-null from the route.

The per-app locale is applied in `Application.onCreate`, which avoids an activity-recreation loop at
startup, but the host is a `FragmentActivity` rather than `AppCompatActivity`, so the AppCompat
per-app-locale path that back-ports to API < 33 has no delegate to drive the resource swap.

WorkManager scheduling in `onCreate` is safe: no custom `Configuration.Provider` and no removal of the
`androidx.startup` initializer, so the default initializer is present when `schedule()` runs. Firestore
usage on startup is async and offline-queued, so it does not throw on launch.

<summary>Details</summary>

### AppLockGate: loop is guarded, but unlock state is lost on recreation

The observer maps `ON_START -> requestUnlock()` and `ON_STOP -> unlocked = false`. The feared
re-lock loop from the biometric/credential dialog backgrounding the activity is actually contained:
when the device-credential UI launches, `MainActivity` gets `ON_STOP` (sets `unlocked=false`, no visible
effect since it was already locked) while `prompting` stays `true`; on return `ON_START` fires and
`requestUnlock()` short-circuits on `if (unlocked || prompting) return`. The success callback then flips
`unlocked=true`. So the guard flags do their job and there is no infinite prompt.

The real defect is state durability. `unlocked`, `prompting`, and `lastError` are `remember`, which does
not survive activity recreation. Any configuration change — rotation, dark-mode switch, font-scale
change, and notably the locale switch this very change introduces — recreates `MainActivity`, resets
`unlocked` to `false`, re-registers the observer, and re-fires `ON_START -> requestUnlock()`. The teacher
is re-prompted for biometrics in the middle of a session. Process death restores the same way. Fix by
promoting the unlock state to `rememberSaveable` (or a `ViewModel`/`SavedStateHandle`) and only
re-locking on a genuine background transition, e.g. tracking whether `ON_STOP` was caused by leaving the
app rather than by recreation.

```kotlin
// AppLockGate.kt
var unlocked by remember { mutableStateOf(false) }   // lost on rotation/process death
```

### School-level report gate resolves to "upgrade required" for everyone

`MainActivity`'s `exam_detail` route constructs the report VM without a subscription manager:

```kotlin
val reportViewModel: ReportViewModel = viewModel(
    key = "report_$examId",
    factory = ReportViewModelFactory(context, repository)   // subscriptionManager omitted
)
```

`ReportViewModel.isSchoolReportAllowed()` is `subscriptionManager ?: return false`, so the Reports tab's
"School-level report" action always lands on `upgradeRequired` and toasts "requires a premium
subscription", even when the user is premium. Individual/class reports are unaffected. Pass
`(context.applicationContext as ExamScannerApplication).subscriptionManager` into the factory. This is a
functional break of a paid feature, not a crash.

### Analytics tab hosts a full-screen panel with its own Scaffold

`AnalyticsTabContent` renders `ItemAnalysisPanel`, whose body is `Scaffold { TopAppBar(...) } { LazyColumn(fillMaxSize) }`
with a back arrow wired to a no-op `onBack`. Placed inside `ExamDetailScreen`'s own `Scaffold` and the
tab `Column`, the `LazyColumn` measures under a bounded height (the outer Scaffold gives the Column a max
height), so there is **no infinite-constraint crash** — the earlier concern about a scrollable panel in a
`Column` does not materialize here because it is a `Scaffold`, not a bare `verticalScroll` Column.

What the user actually sees is two stacked top bars (the exam's TopAppBar plus "Item Analysis") and a
dead back arrow, plus duplicated status-bar insets. For the tab-hosted use, drop the inner
`Scaffold`/`TopAppBar` (extract the `LazyColumn` content into a plain composable) so the tab region hosts
only content.

The sibling `SmartDashboardMVP` fallback is unreachable: the route always passes a constructed
`analyticsViewModel`, so the `if (analyticsViewModel != null)` branch is always taken. `SmartDashboardMVP`
similarly carries its own full-screen `Column` + `statusBarsPadding()` header and would show the same
double-header artifact if it ever rendered.

### Billing: threading is fine; readiness is not guaranteed

`launchBillingFlow` must run on the main thread. The call chain honors this: `SubscriptionViewModel`
launches on `viewModelScope` (Main), `SubscriptionManager.subscribeToPremium` only wraps
`queryProductDetails` in `withContext(Dispatchers.IO)` and returns to Main before
`billingClient.launchBillingFlow(activity, …)`. No main-thread violation.

The gap is connection state. `initialize()` runs on the app IO scope and calls `startConnection`
asynchronously. If the subscription screen is opened before setup finishes (or after
`onBillingServiceDisconnected`, which deliberately does not reconnect), `queryProductDetails` /
`launchBillingFlow` execute against a non-`READY` client and return `SERVICE_DISCONNECTED`. That is
handled as an error state/toast, not a crash, but the purchase silently fails. Consider reconnecting on
demand and reflecting a "billing not ready" state.

The `activity` handed to `launchBillingFlow` is resolved fresh from `LocalContext` at click time, so a
recreated activity is not a stale-reference hazard here.

### Per-app locale applied to a non-AppCompat activity

`applySavedLanguage()` in `Application.onCreate` calls `AppCompatDelegate.setApplicationLocales`. Applying
it before any activity exists avoids a recreation loop at startup (good). But on API < 33 AppCompat
back-ports per-app locales through the `AppCompatDelegate` attached to an `AppCompatActivity`;
`MainActivity` is a plain `FragmentActivity`, so on API 26–32 there is no delegate to swap the activity's
resources and the saved Filipino locale will not take effect in the UI. On API 33+ the framework applies
it regardless. Making `MainActivity` an `AppCompatActivity` (still a `FragmentActivity`, so BiometricPrompt
keeps working) or registering `AppLocalesMetadataHolderService` closes the gap. No crash, but a silent
feature miss on the majority of in-field API levels for this minSdk-26 app.

### Startup ordering that is actually safe (verified, not risks)

WorkManager: `RecycleBinPurgeWorker.schedule` runs in `onCreate`, and there is no custom
`Configuration.Provider` nor any removal of the `androidx.startup` `WorkManagerInitializer` in the
manifest, so the default initializer is present by the time `WorkManager.getInstance` is called — no
"WorkManager is not initialized" crash. Firestore usage from `SessionTracker.initialize()` /
`AnalyticsTracker` on startup is asynchronous and offline-queued by Firestore, so it does not throw when
the device is offline. The `applicationContext as ExamScannerApplication` cast is safe because the
manifest names `.ExamScannerApplication` as the application class.

### Report callbacks with 0/null exam fields do not crash

`onGenerateClassReport` passes `exam.sectionId ?: 0L`; `ReportGenerator.generateClassReport` treats
`sectionId <= 0` as "all students", and `computeClassStatistics` returns zeros for an empty list rather
than throwing on `average()`/`max()`. `onGenerateSchoolReport` uses `exam.subjectFolderId` (defaults to 0)
and aggregates over possibly-empty sections without empty-collection crashes. All generation errors are
caught in `ReportViewModel.runGeneration` and surfaced as an error toast. So these paths degrade to an
empty/So-So report or an error toast, not a crash.
